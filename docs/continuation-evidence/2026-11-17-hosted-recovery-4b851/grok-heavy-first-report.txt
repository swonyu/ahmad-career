Cross-platform usability & accessibility: Arabic/English/RTL, mixed text/URLs, keyboard/large-text/focus/live announcements; Android cancellation

Source/date/evidence: WCAG 2.2 SC 4.1.3 Status Messages (AA, W3C Understanding, 2026): status messages must be programmatically determinable (role or properties) so AT can present them without receiving focus. role=status is the polite live-region technique (ARIA22); role=alert is assertive for critical only. Do not move focus for routine status (results, saved, partial). Focus not obscured (2.4.11). Android HttpsURLConnection.disconnect() can abort blocked reads on modern devices (SocketException) but historically unreliable on older; timeouts are the reliable bound. Supplied Android code uses timeouts, finally disconnect, bounded reads, ensureActive.
User impact: Screen-reader users miss status or have focus stolen; mixed RTL/LTR/URLs unreadable; large text or keyboard order broken; Android search cancel leaves hanging resources or stale UI.
Root cause: Possible incorrect assumption that role=status is a WCAG violation; missing live-region announcements without focus move; hypothesis (not demonstrated crash) on blocking connection cancel.
Direct fix: Use role=status (or aria-live=polite) for routine status without moving focus; reserve alert/focus move for dialogs or critical form errors. Test mixed bidi (dir=auto or proper isolation), large text, keyboard focus order, live announcements. For Android: keep current timeouts + disconnect; if measured slow/trickling fixture shows incomplete cancel, add strict total deadline while preserving prior page.
Realistic alternative: Visual + text status only if AT announcement fails; public board handoff on transport failure. Source hypotheses are not claimed crashes.
Prerequisites/cost/risk: Free; physical VoiceOver/TalkBack remains open gate. Owner: Native and hosted UI owners (coordinate with publisher for device scheduling).

Disagreements with other reviews and why

role=status is not automatically a WCAG violation. Primary W3C SC 4.1.3 requires status messages to be programmatically determinable without receiving focus; role=status (polite) is the recommended technique. Moving focus is generally inappropriate for routine status and can violate predictability (3.2.1). Alerts should not routinely move focus.
Ready receipts must not be labeled Approved (server creates them before approval).
Picomatch advisory lists no patched version; do not treat an unmerged PR as a fix or suppress the audit. Exposure must be examined.
Android HttpsURLConnection cancel is a hypothesis to measure, not a claimed crash.
Live provider checks are diagnostics only.
