## Scope and standard of completion

The intended product is **Career Finder**, a phone app for iOS and Android that starts with a blank profile and works for people across professions and countries. Its core flow should be easy to understand: find a role, save it, prepare a profile, apply through an available route, and keep a useful record of the outcome. Account connection is optional for discovery and local preparation. Automatic submission requires a supported, authorized employer integration and an explicit review of the exact application.

The user requested a strict critique, implementation of the findings, Google sign-in, a LinkedIn connection capability, public HTTPS hosting, repository publication, and a polished app with simple navigation. The latest planning allowance is 24 hours. That allowance does not establish a completion time or a background job: each completed action and test must have an observed result.

This review treats data isolation, accurate submission claims, preservation of drafts, usable phone controls, and truthful release evidence as release requirements. A source fix, a passing synthetic test, a successful hosted deployment, a public preview download, and an app-store release are separate milestones.

## LinkedIn feature and security review

### Delivered scope

The feature stores an optional, user-entered LinkedIn personal-profile URL separately from the website/portfolio field. The phone can open that profile and explicitly open LinkedIn job search with the entered keywords and location. A supported employer submission includes the exact profile URL only when it appears in the application review the person approves.

This implementation does **not** authenticate a LinkedIn account, verify ownership of the profile, import a full LinkedIn CV, scrape LinkedIn, or submit a LinkedIn application. Its labels must continue to say that it is a saved profile link. A true LinkedIn account connection remains an external integration/activation item, not a completed OAuth feature.

## Pending version 5 phone website and browser privacy

Within the user's 24-hour improvement allowance, the hosted work adds a phone-oriented `/phone` interface for Search, Saved, Apply and Profile, with optional home-screen installation guidance. It retains guest discovery/preparation, explicit online profile saving, manual employer handoff, reviewed supported submissions and a private progress record. It does not replace the native iPhone/Android release gates. Opening the website and confirming a signed-in account require a network connection; no offline HTML or personal-data service-worker cache is being introduced.

### Account and transport boundary

The new `/api/phone/` routes use the trusted Sites browser identity. They neither create native phone credentials nor treat a bearer token, request body or caller-supplied account header as browser identity. First workspace GET is read-only, including for an account with no workspace. Explicit opening/creation requires the displayed `expectedAccountId`; all subsequent browser mutations require the current `expectedWorkspaceId`, exact Origin and allowed Fetch Metadata. Receipt export requires one exact workspace query value. These intent checks precede cleanup, throttling, private PDF access and provider work. Native `/api/apply/` pairing remains a separate protocol. See the [browser API contract](Verified-Applications-Contract.md#hosted-phone-browser-api-pending-version-5).

The UI checks that the workspace account matches the server-rendered identity before opening a private browser draft. Returning to a visible page triggers identity confirmation and temporarily conceals private content; an account/workspace change locks the old view. Guest data and older workspace drafts are not adopted silently. ### Encrypted draft storage and reset

The vault stores profile drafts, the optional PDF copy, saved jobs, private records and bounded previous-search results in IndexedDB. Scopes are exactly `guest` or `account:<encoded account ID>:<workspace UUID or new>`. Each successful write uses a new non-extractable AES-GCM-256 key and 12-byte IV; the encrypted envelope authenticates its schema, scope, revision and time. The key is stored through IndexedDB structured cloning. No plaintext profile/PDF/note fallback is written to localStorage or a service-worker cache.

Per-scope operation ordering and a transactional compare-and-swap protect against late writes and another tab's changes. A changed stored revision requires explicit reload; export does not adopt that revision or clear a storage failure. Invalid, damaged or future-schema bytes are preserved, with writes blocked until deliberate recovery/reset. Storage/quota errors remain visible instead of being reported as successful saves. The 20 MiB envelope cap is a defense in depth; model limits remain stricter.

An explicit reset deletes private ciphertext and its key, leaving only an opaque revision/time marker so a stale empty tab cannot recreate erased data. Markers are not listed as saved drafts. A damaged-data recovery export may contain ciphertext without an exportable key; the non-extractable key remains in the original browser, so that file alone is not a portable restoration promise. Browser encryption protects stored data, not a compromised script running on the same origin or an unlocked compromised browser. [Frozen vault contract and limits](strict-review-evidence/phone-vault-source-review.json).

## Rules for updating this ledger

Only change a pending item to complete after recording its exact source/artifact and an observed result. Add a later successful run beside a failure; do not rewrite the failure into a success. Keep original provider receipts separate from user-entered tracking records. Keep synthetic, test-mode, unsigned, preview, deployed and store-released evidence distinguishable.
