## Evidence and provider boundary

The first real connector implements [Lever's official Postings API](https://github.com/lever/postings-api). Global and EU hosts are separate. An employer-authorized key is required per employer site. Successful submission means exactly HTTP 200 and a JSON object containing `ok: true` and a nonempty string `applicationId`. The identifier proves API acceptance, not recruiter review or a job offer. Redirects, timeouts, 5xx and malformed success responses are unconfirmed and must never be automatically retried. HTTP 429 explicitly rejects a request; retry requires the recorded cooldown to finish and a fresh, explicit approval of the still-current review. Custom questions are not exposed by this API; employer-controlled, current posting requirements must explicitly establish that the supported standard fields are sufficient. Unknown/custom requirements block dispatch. PDF résumé bytes must be uploaded as multipart form data.

## Deployment and sessions

The operator-managed API service runs from `website/applications/server.mjs` under `/api/apply/`. It binds exclusively to 127.0.0.1, default port 8780. The hosted service implements the same phone session/review protocol and exposes browser pages for phone connection and account controls. iOS and Android require HTTPS and a server-issued, single-use pairing code. Phones without an activated service retain preparation and manual employer links.

Every application route validates the configured Host/origin boundary. Native sessions use an expiring bearer token whose hash alone is retained by the server. Pairing codes expire after five minutes. Hosted codes are issued through an authenticated, account-bound connection action; the operator-managed companion issues them through its administrator CLI. No unauthenticated HTTP route can issue a code. Native tokens expire after 30 days and can be revoked through `POST /api/apply/session/revoke`. Native bearer requests do not use browser Origin/CSRF headers. Both native clients retain tokens in platform secure storage.

The companion's loopback browser tests use a private HttpOnly SameSite=Strict session cookie, exact Origin, JSON and an `X-Career-CSRF` token for state-changing requests; initial bootstrap still requires exact Origin and JSON. Each such test browser session owns a separately identified workspace. HTTPS companion deployments reject anonymous browser workspace creation and never enable a CORS wildcard. These companion cookie/CLI rules are distinct from the hosted service's Sites-owned sign-in and browser routes below.

Hosted sign-in uses the platform account, with Google offered on the secure ChatGPT sign-in screen where available. The application does not claim a separate direct Google OAuth implementation. Native default setup is two steps—sign in/get a code, then paste/connect—with custom HTTPS services under Advanced. Connection does not automatically upload an unfinished phone profile or adopt another workspace's private records.

The SQLite ledger is outside `web/`, with private permissions and durable transactions. A process lock prevents two companion instances recovering each other's active dispatches. Restart changes leftover dispatching attempts to uncertain. Test instances use separate data directories and a separately labeled test connector; fixture receipts never enter real data.

The operator-managed companion does not verify applicant email ownership. Duplicate protection and cooldown history are confined to one workspace. Pair additional phones to the same workspace to share that protection; an editable email never grants access to another workspace's application history. The hosted service checks across workspaces only when the applicant email matches the confirmed account email. It retains same-workspace duplicate protection after profile-email changes. The companion migration removes the old global applicant index without deleting application records.

Hosted browser pairing requires the displayed `expectedAccountId`. Deletion, phone revocation and interrupted-upload recovery require the displayed `expectedWorkspaceId`; export and PDF downloads carry it as a single query parameter. A stale, missing or ambiguous target fails before changing records or reading a private file. Account GET remains read-only and reports both the current sign-in email and the workspace's confirmed email; explicit pairing refreshes a changed email and invalidates older approvals through a new profile revision. Pairing responses contain server-relative expiry information so an inaccurate phone clock cannot extend a code's validity.

## Native and companion API contract

All JSON responses use `{ok:true,...}` or `{ok:false,error:{code,message}}`. Errors are sanitized. Unknown request properties are rejected. Missing sessions return 401; denied Origin/Host/CSRF return 403; stale revisions or duplicate attempts return 409; validation errors return 422; oversized payloads return 413. The browser never supplies a submission outcome or trusted provider configuration.

| POST /api/apply/session/revoke | `{}` with native bearer | Revoke this phone token while retaining workspace data |

| POST /api/apply/jobs | `{url,title?,company?,location?,country?}` | Saved opportunity. Lever URLs import exact public posting metadata. Other public HTTPS URLs need explicit title/company and are manual-only; they are never fetched by the server. |
| POST /api/apply/prepare | `{jobIds,answers?,manualAppliedJobIds?,reviewSchema?:3}` | Immutable plan `{id,digest,profileRevision,items,expiresAt}` with per-job eligibility and exact shared fields/CV metadata; no dispatch. `answers` keyed by job ID, only comments, consentStore, consentMarketing; no inferred consent. Profile fields: firstName, lastName, email, phone, city, country (ISO alpha-2), headline, skills (string array), targetRoles (string array), targetCountries (string array), workModes (on-site/hybrid/remote), experienceLevel (entry/mid/senior/any), website (optional public HTTPS URL), linkedin (optional validated personal-profile URL), resume (optional `{name,mime:'application/pdf',dataBase64}`; omitted means preserve, null means remove). Required for automatic submission: first or genuine single name, valid email, PDF with matching magic bytes and ≤5 MiB. A separate last/family name is optional; the review and multipart upload use the same trimmed name without inventing a surname. First save uses expectedRevision 0. Unknown fields, malformed strings, invalid enumerations and filesystem paths are rejected. Profile revision changes invalidate prepared approvals. The immutable payload, résumé digest and provider requirements revision are recorded before sending.

## Hosted phone browser API (deployed version 6)

The phone website uses a narrow `/api/phone/` route set under the same HTTPS origin. Trusted Sites identity selects the account; native bearer tokens, payload fields and caller-supplied identity headers cannot select a browser owner. The trusted edge must remove untrusted caller identity headers before supplying authenticated values. Local workerd tests model that edge; deployed edge acceptance remains a release gate.

All writes require exact Origin, JSON and allowed same-origin Fetch Metadata. The account/workspace intent is validated before cleanup, quota/throttle writes, PDF access or provider requests. Unknown fields and unsupported methods/routes are rejected. In-progress account deletion blocks creation, mutations and receipt exports while leaving its read-only status visible. A changed confirmed email requires an explicit account-bound refresh, which advances profile revision and invalidates old approval.

The page must verify the API account against its server-rendered identity before loading an account vault. Visibility return temporarily hides private content while it checks the same account/workspace; identity mismatch locks the old view. Asynchronous export/results must recheck scope and request generation before presentation. A newer confirmed workspace cannot be overwritten by an older initial response. The privacy curtain keeps dirty modal children mounted, prevents dismissal while checking, and uses explicit discard confirmation for unfinished record/Add forms. ## States and authority

Each attempt records `evidenceMode: live` or `test`; tests and real data cannot share a ledger. A phone must not count missing/unknown evidence mode as a live receipt.

`ready` → `dispatching` → `confirmed`, `uncertain`, `rejected` or `rate_limited`. `ready` → `cancelled` when stopped. Unsupported/incomplete items are `blocked`. Confirmed, uncertain and dispatching attempts block further automatic submissions for the same canonical job within the applicable ownership scope. A stable workspace identity also blocks duplicates after email changes. A rate-limited attempt records the next permitted retry and never retries before it; retries require fresh explicit approval of the still-current review and a bounded attempt count. Definite rejection is presented for correction. Clicking or opening an employer link cannot create a receipt. The phone UI does not enable a new live approval unless the authenticated workspace explicitly reports live submission availability; labeled synthetic test mode remains separate.

Receipt fields: attemptId, provider, region, employerSite, postingId, employer/title, applicationId (confirmed only), state, createdAt, dispatchedAt, confirmedAt, profileRevision, resumeSHA256, payloadSHA256, requirementsRevision, responseSHA256 and sanitized error. Export identifies mock/test evidence explicitly. Raw authorization, API key query strings, CV bytes and raw provider errors are never logged/exported.

## Configuration

Server-side connector configuration is read from an explicitly provided private file (`CAREER_APPLY_CONFIG`) outside static assets. Each entry binds region, employer site, API-key environment-variable name and reviewed posting IDs. Each posting has a current requirements revision, reviewedAt, expiresAt, requiredFields and hasCustomQuestions:false. Only supported fields may be required. An absent/expired/unknown requirements manifest disables auto submission and leaves manual application available. Config never contains an unrestricted user-provided POST URL. Real outbound hosts are fixed to api.lever.co and api.eu.lever.co. Response redirects are disabled.

For required consent fields, `consentMarketing` requires an explicit boolean answer; `false` is a valid declined future-contact choice and is sent unchanged. A required `consentStore` requires explicit positive permission and an available employer policy. Unanswered values are never inferred, and agreeing to application processing does not imply future-contact permission.

## Phone recovery

GET workspace returns current, unexpired, unstopped reviews with ready or explicitly rate-limited attempts, limited to the authenticated workspace. Recovering a review restores its original digest and current item states; it neither approves nor sends it. Both phone clients require a new visible review/approval to resume after a provider cooldown. Unknown outcomes remain blocked.

Replacing an unapproved review is deliberate: stop that exact earlier plan using `onlyIfUnapproved:true`, then prepare the new inputs. The condition and stop occur in one transaction. If another phone approved the earlier plan in the meantime, the replacement must pause and refresh its current state. A client-side check alone cannot authorize cancellation of an approved review. Ordinary explicit Stop omits the condition and retains the existing batch-stop behavior.

### Approved browser continuation and expired claims (deployed version 6)

The browser continuation helper never grants approval. It captures the account, workspace, plan digest and profile revision, then continues only while the exact plan remains approved and appears in current `activePlanIds`. It awaits each advance, permits at most 20 calls per invocation, and spaces successful steps by one second. It rechecks visibility, Stop, expiry, current profile and manual-application guards before another dispatch opportunity. Missing details, errors, unchanged progress, active dispatch claims or loss of current approval pause the loop. Hidden-page/background execution does not keep sending work. A rate-limited item cannot resume merely because its clock elapsed; the service must report a current eligible reapproval.

Explicit Stop is a different action from hiding or closing the page. Its version 6 server transaction stops the exact owned plan, cancels that plan's ready/rate-limited work, and changes only its already-expired dispatch claims to `uncertain` with `worker_interrupted`. Live claims remain able to record their real provider result. Another plan's or workspace's claims remain unchanged. A guarded `onlyIfUnapproved` refusal must leave all these states untouched, including when an already-approved plan was stopped earlier. Repeating an ordinary explicit Stop may reconcile a claim that expired later.

The stop transaction is atomic: a later statement failure rolls back earlier cancellation. A late provider response cannot overwrite an expired claim that has already been reconciled as uncertain. Read-only browser workspace/receipt GETs and a denied advance/guarded Stop do not perform that repair. Uncertain claims remain duplicate-blocking and are never automatically resent. ## Private application records (native 0.6 and deployed phone website)

Saved, Applied, Interview, Offer and Closed describe the person's own record. Optional applied/follow-up dates and a private note help track an application completed on an employer site. They remain clearly labelled as stored on this phone/browser. A manual mark, date, link opening or note cannot create a verified receipt, live application count or provider acceptance claim. Private notes and follow-up dates never enter the employer payload.

Dates use validated civil `YYYY-MM-DD` values; blank means unknown. No timestamp or time-zone conversion invents an applied date. Applied/Interview/Offer set a durable `appliedElsewhere` mark, and Closed preserves it. Saving a previously applied record as Saved requires explicit “Mark as not applied?” confirmation, explaining that the change affects this private record, not an employer-held application. Cancel writes nothing. Restoring an archived version's details after that deliberate correction cannot reinstate the old mark. A fresh explicit applied-stage save or deliberate import of new applied evidence can.

Native records are scoped by exact normalized HTTPS service origin, workspace ID and canonical job identity. Matching local/service IDs retain one job identity without dropping history. Colliding record versions are preserved for explicit comparison; choosing notes/dates cannot silently clear combined current applied evidence. Editor, removal and association actions recheck workspace/connection generation and record revisions before persistence. Future or damaged persisted schemas must be preserved rather than reset automatically.

Removing a bookmark leaves meaningful private notes/status/history visible as an application-record-only entry. It does not withdraw an application or erase a remote receipt. Pairing never silently moves unpaired data. iPhone's explicit “Keep with connected workspace” confirmation associates the selected unpaired versions with the exact current workspace, even when the bookmark was removed and that workspace already contains the job. It retains collisions and removed-bookmark state without uploading notes. Android's explicit draft-copy operation likewise includes retained record-only entries without recreating their bookmarks. Private data from a different account/origin is never automatically adopted.

Every prepare/recover/reapprove path must consult the current durable applied mark, including canonical duplicate links. Changing that mark for a job in an active approved plan requires Stop first; unknown active plan/target details fail closed. Note/date edits that preserve the mark can continue. Inactive cooldown-only reviews may be edited, but a newly marked job is excluded when the review is next approved. Defensive continuation also refuses a ready/rate-limited target already marked applied, including restored legacy combinations; it must not invent a Stop request or false receipt to do so.

## Encrypted browser draft vault (deployed version 6)

The phone website keeps local drafts distinct from explicit online profile saves. Its storage API provides `loadPhoneSnapshot`, `savePhoneSnapshot`, `exportPhoneSnapshot`, `removePhoneSnapshot` and metadata-only `listPhoneSnapshots`. Valid scopes are exactly `guest` or `account:` plus the canonical encoded account ID and the workspace UUID/`new`. Listing requires the exact same-account prefix. The UI confirms the signed-in account and workspace before loading, displaying or exporting an account scope; metadata discovery never authorizes cross-account access or automatic adoption after workspace recreation.

IndexedDB holds a versioned AES-GCM-256 envelope and a structured-cloned, non-extractable CryptoKey. Each write uses a fresh key and 12-byte IV and authenticates the schema, exact scope, envelope revision and time as additional data. Snapshot parsing rejects unsupported/malformed content before persistence; the plaintext envelope is capped at 20 MiB in addition to model limits. No plaintext PDF/profile/note, localStorage fallback or service-worker personal-data cache is used. The website requires network access to open/confirm an account; this is not an offline HTML caching contract.

Operations serialize within each scope, capturing a save's input immediately. An IndexedDB transaction compares the stored envelope ID with the revision observed by the last successful load/save before committing a new envelope/key pair. Another tab's change rejects the save without overwriting it and requires explicit reload. Export never advances that expected revision, adopts another tab's state or silently unblocks a damaged snapshot. Storage/quota errors surface as unsaved state, not a successful save.

The UI action is **Export phone data**. A valid export is a readable JSON snapshot; the current release has no restore/import screen. Labels, filename and explanatory copy must not describe it as a restorable backup. The direct saved-data/home-screen headings and this export clarification are in PhoneApp SHA-256 `2732dc09e630949cdae226ecf2e6e5acf32856ed28bee4944f61ce91cdf80b21`, covered by the fresh initial SSR and deployed version 6 package. Actual browser interaction remains a separate acceptance check.

Corrupt, unreadable or future-version bytes remain preserved and block writes until explicit recovery/reset. Valid exports contain the parsed snapshot. Recovery exports are labelled with their limitations: unreadable encrypted content does not include the non-extractable key, which remains in the original browser, so that file alone cannot restore elsewhere. Reset requires a deliberate UI confirmation; it deletes private ciphertext and key and leaves only scope plus an opaque revision/time marker. The marker prevents a stale tab that previously saw an empty scope from resurrecting erased content, is hidden from draft lists, and loads as no snapshot. Caller UI must cancel stale pending actions on identity changes/reset.

This encryption addresses stored browser data. It does not promise protection against arbitrary script execution on the same origin or a compromised unlocked browser. The 27 passing Node WebCrypto groups exercise actual encryption and structured-cloned keys with an injected atomic store, including a maximum valid populated profile/jobs/records/search/PDF snapshot. Real browser IndexedDB/key-clone durability, two-tab conflicts, quota behavior and production reset/export still require acceptance. ## LinkedIn profile links and compatible review approval

`profile.linkedin` is an optional personal profile URL, separate from `website`. A new workspace returns an empty value. Older clients may omit the field without erasing a saved link; explicitly sending an empty string clears it. Canonical links use HTTPS on `www.linkedin.com/in/<slug>` with one validated Unicode slug, percent-encoded as RFC 3986 unreserved UTF-8. Country-host variants and tracking query/fragment components are canonicalized. Credentials, custom ports, path ambiguity, encoded separators, invalid UTF-8, control/format characters, and canonical URLs longer than 2,048 characters are rejected before persistence.

`capabilities.linkedinProfile: true` confirms server support for this optional field. New phone clients preserve drafts and refuse to sync a nonblank link, or clear a known saved link, until support has been confirmed. An absent field in an older server response means blank; a present malformed value invalidates the response rather than replacing a valid draft.

If a saved profile has a LinkedIn URL, preparation requires `reviewSchema: 3` before the item can be ready. Submission and reapproval of a plan containing a LinkedIn URL also require `reviewSchema: 3`; without it the service returns `409 review_update_required` before approving or sending. This protects a review recovered by an older phone. `payloadSummary.linkedin` displays the exact URL. Phone clients check that actionable review items match the current profile. The immutable provider snapshot and `urls[LinkedIn]` multipart field use that same approved value; `urls[Portfolio]` remains separate. Editing or clearing the profile advances its revision and invalidates earlier approval.

Saving a link is not LinkedIn OAuth, verified account ownership, CV import, or authorization to apply on LinkedIn. Search LinkedIn is an explicit external navigation with only the user's public keyword/location filters. Saved LinkedIn job URLs remain manual opportunities and are never fetched by the submission adapter or converted into verified application receipts.
